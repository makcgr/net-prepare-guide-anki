What are the five steps for answering a technical question?	<ol><li>Clarify the question</li><li>Answer first, in 1-2 sentences</li><li>Explain the why (mechanism)</li><li>Show an example or real story</li><li>State the tradeoff or limit</li></ol>Then stop and let the interviewer choose where to go deeper.	ch14 how-to-answer
Why should you think aloud in a technical interview?	Silence looks like being stuck, and the interviewer scores your reasoning, not only the final answer. Say what you are checking and why.	ch14 how-to-answer
What is a strong way to answer when you do not know something?	Say you do not know, then reason from what you do know, and say how you would check (docs, benchmark, test). Never invent API names or numbers.	ch14 how-to-answer
Why answer first and explain after?	The interviewer gets the signal at once and can steer. A long build-up hides the answer and wastes the time you have for depth.	ch14 how-to-answer
Kafka consumer safety: what separates a Senior answer from a Mid answer?	Mid: catch and retry. Senior: at-least-once delivery, so idempotent handler (processed event ids, unique index, same transaction as the side effect) and a DLQ for poison messages.	ch14 how-to-answer kafka levels
Kafka consumer safety: what does a Staff-level answer add?	Ordering per key (partition key), validation vs transient errors, alerts routed to the owning team, and a replay runbook. At Smartcat: <code>SingleEventWithIdempotencyKeyProcessorBase</code>, <code>EventHandlerException(responsibleTeams, e)</code>.	ch14 how-to-answer kafka levels smartcat
What does STAR stand for?	Situation, Task, Action, Result. Situation and Task are short context; Action is what <b>you</b> did and why; Result has a number if possible and what you learned.	ch14 behavioural star
What is the most common mistake in STAR answers?	Saying &quot;we&quot; for everything, so the interviewer cannot see your own actions and judgment. Also: a result that is only &quot;then the team did it&quot;.	ch14 behavioural star
Which 6-8 behavioural stories should you prepare?	A production incident, a disagreement, a mistake you made, mentoring, pushing back on scope, a cross-team change, a decision with incomplete data, a process you improved.	ch14 behavioural
How do you answer &quot;Tell me about a mistake you made&quot;?	A real mistake with real impact, in STAR. Show how you fixed it and what you changed to prevent it (a test, a rule, a process). No blaming others.	ch14 behavioural
Live coding: what do you do before you type?	Restate the problem and signature; ask about size, nulls, empty input, duplicates, order; write 2-3 examples with one edge case; say the simple solution and its complexity first.	ch14 live-coding
Live coding: what do you do after the code is written?	Walk through your examples out loud, check edge cases (empty, one item, all equal, large, null), state time and space complexity, name 2-3 tests, mention production changes.	ch14 live-coding
Top-k frequent words: why a min-heap of size k instead of sorting?	Selecting with a heap of size k is O(m log k) for m distinct words; a full sort is O(m log m). In .NET: <code>PriorityQueue&lt;string, int&gt;</code>, dequeue when <code>Count &gt; k</code>.	ch14 live-coding complexity
What C# guard clauses are idiomatic at the start of a public method (.NET 8)?	<code>ArgumentNullException.ThrowIfNull(x)</code>, <code>ArgumentOutOfRangeException.ThrowIfNegative(n)</code>, <code>ArgumentException.ThrowIfNullOrEmpty(s)</code>. Then return early on empty input.	ch14 live-coding csharp
System design: in what order do you work through the prompt?	1. Clarify requirements (functional and non-functional). 2. High-level flow. 3. Component boundaries (monolith vs service). 4. Deep dives (data, reliability, scale, security). 5. Tradeoffs and next steps.	ch14 system-design
File translation pipeline: name the main steps of the flow.	Upload (stream to object storage) → Document + event via outbox → disassembly background task → segments stored → <code>DocumentDisassembled</code> event → idempotent consumer creates translation tasks → read model for the UI → assembly task builds the translated file.	ch14 system-design pipeline smartcat
Which non-functional questions do you ask before designing a file pipeline?	File size range, number of tenants and fairness, latency expectations (sync vs async), reliability (no lost files, no duplicates), how often formats change, parser crash behaviour.	ch14 system-design
In a system-design interview, how do you name and explain the dual-write problem?	You save state to the database and then publish to the broker; if the process dies in between, the event is lost (or published without the state). The two writes are not atomic.	ch14 system-design outbox
How does the outbox pattern solve dual writes at Smartcat?	The entity (<code>DomainEntity</code>) calls <code>AddEvents</code>; events are saved in its <code>mqEvents</code> field in the same atomic Mongo update as the state. An outbox processor publishes them to Kafka later.	ch14 system-design outbox smartcat
Why must the outbox repository use <code>PushEach</code> and not <code>Set</code> for events?	<code>Set</code> overwrites the events array, so concurrent updates lose each other's events. <code>PushEach</code> appends atomically.	ch14 system-design outbox smartcat
What does the second argument of <code>[MqEvent(&quot;document-uploaded&quot;, nameof(DocumentId))]</code> do?	It is the order group property. It becomes the Kafka partition key, so all events of one document are processed in order.	ch14 system-design kafka smartcat
Why must a Kafka consumer be idempotent?	Delivery is at-least-once: rebalances, retries and replays deliver the same event again. Without idempotency you get duplicate side effects, for example duplicate tasks.	ch14 system-design idempotency
How does Smartcat's idempotent handler base class work?	<code>SingleEventWithIdempotencyKeyProcessorBase&lt;T&gt;</code> checks (handlerName, eventId) in a processed-events collection; if new, it runs the handler and inserts the processed record in one transaction. Records expire by TTL.	ch14 system-design idempotency smartcat
What is the second line of defence against duplicate tasks besides processed-event ids?	A unique index on the business key, for example <code>UDX_DocumentId_TargetLanguage</code> on the tasks collection.	ch14 system-design idempotency mongodb
Why is disassembly a background task and not done in the upload request?	It is slow, CPU and memory heavy, and can crash on bad files. A task survives restarts, retries with backoff, and moves to Manual state after the retry limit, while the request returns quickly.	ch14 system-design background-tasks
How do you keep one customer with 5,000 uploads from slowing down everyone else?	Fairness hash on the task, for example by (accountId, documentId). Workers round-robin across accounts instead of processing in pure arrival order.	ch14 system-design background-tasks fairness
How do you roll out a new parser version safely in the task pipeline?	Canary by <code>TierKey =&gt; AccountId.ToString()</code>: a small percentage of accounts goes to canary workers, and the same account always stays in the same tier.	ch14 system-design canary smartcat
What happens to a poison file in a well-designed task pipeline?	After the retry limit, the task moves to Manual state with a reason and an alert fires. The rest of the queue keeps moving.	ch14 system-design background-tasks
Why store segments in their own collection, not as an array in the document?	Large files have hundreds of thousands of segments; an unbounded array grows past the 16 MB document limit and is expensive to index and update. Use a <code>segments</code> collection with <code>UDX_DocumentId_Number</code>.	ch14 system-design mongodb
Why build a read model for the project list?	Joining several modules per request breaks bounded-context rules and is slow. A consumer builds a denormalized list from events. It is eventually consistent, which is fine for a list page.	ch14 system-design read-model
Name four criteria for extracting a module into a separate service.	Different scaling profile, need for failure isolation, one team owns it end to end, its own release cadence, and it owns its data (others need only events).	ch14 system-design architecture
What does extracting a service cost?	Network calls and failures, contract versioning (additive changes only), eventual consistency instead of one transaction, more deployment and monitoring work.	ch14 system-design architecture
Why is file disassembly a good candidate for its own service?	Parsers are CPU and memory heavy, sometimes crash on bad input, need their own scaling and fast releases for new formats. At Smartcat this is the File Disassembling service (<code>filedisassembling/</code>).	ch14 system-design architecture smartcat
What makes a module cheap to extract from the monolith later?	Honest boundaries: it owns its collections, others use only its published contract or events, and there are no dependency cycles. A module that is read through its tables is expensive to extract.	ch14 system-design architecture smartcat
System design: which metrics show that the file pipeline is healthy?	Queue depth and oldest task age per state, consumer lag, DLQ size, outbox backlog, parse time per format, and the trace id carried from upload to task to events.	ch14 system-design observability
What are common mistakes in a system design round?	Drawing boxes before asking about scale and tenancy; &quot;we use Kafka&quot; without duplicates or crash handling; microservices with no reason per service; no indexes; forgetting authorization.	ch14 system-design
What is a good method for a 15-minute code-review exercise?	Read once fully; then go by category (correctness, security, concurrency/async, resources, design, tests, style); rank by severity; for each finding give problem, consequence, fix.	ch14 code-review
Define the four review severities.	BLOCKER: security hole, data loss, crash. MAJOR: real bug under load or edge case, or costly design. MINOR: maintainability, small performance, missing non-critical test. NIT: style and naming.	ch14 code-review severity
What is wrong here?<pre><code>services.AddSingleton&lt;ExportService&gt;();<br>services.AddScoped&lt;IDocumentRepository, DocumentRepository&gt;();<br>// ExportService takes IDocumentRepository in its constructor</code></pre>	Captive dependency (rule A1, BLOCKER): the singleton holds a scoped repository forever, shared by all requests and threads. Make the service scoped, or use <code>IServiceScopeFactory</code> in a true background component.	ch14 code-review di
What is wrong here?<pre><code>[HttpPost]<br>public IActionResult Start([FromBody] StartExportRequest request)<br>    =&gt; Ok(_service.Start(request.AccountId, request.DocumentIds));</code></pre>	No <code>[Authorize]</code> on a write endpoint (S20), and the tenant id comes from the body with no ownership check (S2/S14): a user can act on another customer's data. Take the account from the authenticated user.	ch14 code-review security
Why is <code>Path.Combine(&quot;/data/exports&quot;, fileName)</code> with client input dangerous?	Path traversal (S9): <code>../../x</code> escapes the folder, and an absolute <code>fileName</code> makes <code>Path.Combine</code> ignore the first part. Generate file names on the server.	ch14 code-review security
What is wrong with <code>_service.StartAsync(...).Result</code> in a controller?	Sync over async: it blocks a thread-pool thread for the whole operation; under load this causes thread-pool starvation. Make the action <code>async Task&lt;IActionResult&gt;</code> and await.	ch14 code-review async
Why is <code>private async void notifyAsync()</code> a problem?	An exception that escapes crashes the process (no Task to observe it); callers cannot await it; the work is lost on restart. Use a background task or an outbox event.	ch14 code-review async
What is wrong with a <code>static Dictionary&lt;Guid, int&gt; _progress</code> in a web service?	Not thread-safe: concurrent writes can corrupt it. And it is per pod: with several pods each returns a different answer. Store progress in the database.	ch14 code-review concurrency
What is wrong with <code>using var client = new HttpClient();</code> per call?	Socket exhaustion under load (TIME_WAIT), no DNS refresh, no timeouts or resilience. Use <code>IHttpClientFactory</code> with a typed client.	ch14 code-review resources
What is wrong here?<pre><code>foreach (var id in documentIds)<br>    texts.Add((await _documents.GetByIdAsync(id)).Text);</code></pre>	N+1 reads (A20): one database round trip per id. Load all with one query (<code>FindByIdsAsync(ids)</code>, filtered by account). Also: a missing document gives a NullReferenceException.	ch14 code-review performance
A test calls an async method without <code>await</code> and then <code>Thread.Sleep(1000)</code>. What is wrong?	Slow and flaky: the result depends on timing. Make the test <code>async Task</code> and await the call.	ch14 code-review tests
Why is reading a private field by reflection in a test a bad idea?	It pins the implementation: a rename breaks the test at run time, not at compile time, and refactoring tools do not see it. Assert public behaviour, or extract the hidden piece into an injected dependency.	ch14 code-review tests
Code review exercise: what should a strong candidate say first about the export snippet?	The blockers: missing auth, tenant id from the body, path traversal, singleton holding a scoped repository. Then async problems. Then the design fix: export as a background task with state in the database.	ch14 code-review
Interviewer: what is a structured interview?	Every candidate for a role gets the same core questions, in the same order, scored with the same written rubric. It is the most reliable way to compare candidates and reduce bias.	ch14 interviewer structured
Interviewer: how do you split a 60-minute technical round?	5 min intro and format; 10 min warm-up on the candidate's own system; 30 min for 2-3 core questions with probes; 10 min scenario; 5 min candidate questions. Write notes right after.	ch14 interviewer plan
Interviewer: name four depth probes that work for any topic.	What if this runs on three pods at once? What if the process dies right here? How would you know in production that it is broken? What would you test first?	ch14 interviewer probes
Interviewer: how do you tell a Senior from a Staff answer by the scope of the example?	Senior: &quot;I fixed the handler.&quot; Staff: &quot;I fixed it, found the same pattern in six handlers, and made the base class prevent it.&quot;	ch14 interviewer levels
Interviewer: how do Senior and Staff candidates differ on tradeoffs?	Senior names the tradeoffs. Staff names them, picks one, and says which signal would make them change the decision.	ch14 interviewer levels
Interviewer: why not average scores across dimensions?	Averaging hides a critical gap. One BLOCKER-level gap (for example no idea of tenant isolation for an API owner) can decide the result.	ch14 interviewer rubric
Interviewer: list the rubric dimensions for a .NET backend role.	C# and runtime; async and concurrency; design and architecture; data and storage; testing; code review and quality; security; communication; ownership and impact.	ch14 interviewer rubric
Interviewer: what is calibration?	Interviewers give the same score for the same performance. Tools: shared questions and rubric anchors, shadowing and reverse-shadowing, written evidence before the debrief, review of past hiring decisions.	ch14 interviewer calibration
Interviewer: what is the halo (or horns) effect, and the countermeasure?	A strong or weak first answer colors the whole interview. Score each question separately, right after it.	ch14 interviewer bias
Interviewer: what is confidence bias?	A confident wrong answer beats a careful right one. Check facts, and reward &quot;I am not sure, here is how I would find out&quot;.	ch14 interviewer bias
Interviewer: how do you avoid language bias with second-language speakers?	Use short, idiom-free questions, rephrase when the candidate looks unsure, and judge the engineering content, not fluency. A misunderstood question is noise, not signal.	ch14 interviewer bias smartcat
Interviewer: what is anchoring in a debrief, and how do you prevent it?	The first person who speaks sets the result. Everybody submits written feedback before the debrief and reads their evidence before hearing others.	ch14 interviewer bias
Interviewer: what is the structure of good written feedback?	Evidence, then interpretation, then a decision. Recommendation and level, short summary, evidence per dimension with what the candidate said or did, open concerns, &quot;no signal&quot; where you have none.	ch14 interviewer feedback
Interviewer: what is wrong with &quot;good culture fit, solid engineer, hire&quot;?	No evidence: it cannot be checked, compared or defended. Write what the candidate did, for example &quot;explained the dual-write problem without a prompt&quot;.	ch14 interviewer feedback
Interviewer: name three things that must never appear in feedback.	Protected characteristics (age, family, origin) or guesses about them, comments on accent, and vague adjectives without evidence.	ch14 interviewer feedback
Interviewer: how do you pick questions to find a candidate's range?	In each round, one question in an area where the candidate is strong (finds the ceiling) and one where they are weaker (finds the floor).	ch14 interviewer plan
Interviewer: name four green flags across rounds.	Clarifies before designing or coding; states assumptions and tradeoffs unasked; changes their mind with new data and says why; knows the limits of their knowledge.	ch14 interviewer
Interviewer: name four red flags across rounds.	Answers a different question twice; no tradeoffs for their own design; blames others in every story; invents API names or numbers.	ch14 interviewer
Interviewer: a candidate proposes reading another module's Mongo collection directly in the design round. Why is that a red flag at Smartcat?	It breaks the mandatory bounded-context rules: a module owns its model, and cross-module communication goes only through contracts or events (<code>smartcat/.claude/rules/bounded-contexts.md</code>).	ch14 interviewer architecture smartcat
Interviewer: which chapters feed which interview rounds?	Screening: 01, 03, 05. Live coding: 01, 03, 10. Deep dive: 03, 04, 07, 08, 09, 10. System design: 06, 07, 08, 09. Code review: 12, 13, 10.	ch14 interviewer plan
